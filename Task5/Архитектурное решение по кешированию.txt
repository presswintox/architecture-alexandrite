Мотивация:
Система MES испытывает значительные проблемы с производительностью, особенно при загрузке страницы со списком заказов.
 
Основные проблемы:
- Высокая нагрузка на сервер MES из-за частых запросов от операторов и API-клиентов.
- Медленная загрузка страницы с заказами, даже после введения пагинации и фильтров. Операторам важно быстро получать информацию о заказах.

Цель кеширования — снизить нагрузку на сервер MES, ускорить отклик интерфейса для операторов и API-клиентов, улучшить опыт пользователей и уменьшить количество жалоб.

Предлагаемое решение:
Серверное кеширование — предпочтительный вариант, так как:

- Данные используются разными клиентами (MES, CRM, Внешнее API).
- Кеш централизован и управляем.
- Можно использовать Redis как быстрый кеш с TTL и инвалидацией.

Паттерн кеширования: Cache-Aside

- При запросе данные сначала ищутся в кеше.
- Если данных нет, происходит обращение к источнику (например MES DB), затем данные записываются в кеш.
- При изменении данных (например, изменение статуса заказа) кеш инвалидируется.

Почему Cache-Aside?
- Самый быстрый и простой в реализации паттерн.
- Хорошо подходит для сценариев с нерегулярными изменениями данных.
- Позволяет точно контролировать, когда обновлять кеш.
- Write-Through слишком нагружает производительность при записи, а Refresh-Ahead сложен в реализации и может приводить к лишним обновлениям.

В диаграмме последовательности действий[sequence.puml] показано, как будет работать кеширование для чтения списка заказов и запись об изменении статуса заказа.

Стратегия инвалидации кеша
- Инвалидация по ключу — при изменении статуса заказа удалять кешированную запись.
- Временной TTL — на всякий случай установим небольшой TTL (например, 10-15 минут), чтобы избежать устаревания данных при возможных ошибках в инвалидации.
- Не использовать только временную инвалидацию, так как данные должны быть максимально актуальными.
