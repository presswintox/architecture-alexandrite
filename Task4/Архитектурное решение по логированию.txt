Мы планируем настроить логирование в сервисах MES API, CRM API и SHOP API, так как основная нагрузка и бизнес-логика приходится на бэкенд сервисы, и важно отслеживать их логи для быстрого выявления проблем.

Необходимые логи INFO: 
- Изменение статуса заказа (timestamp, order_id, user_id, old_status, new_status).
- Действия операторов MES (timestamp, operator_id, action, order_id, details).
- Запросы к API (timestamp, endpoint, method, user_id, response_time, status_code).
- Аутентификация и авторизация (timestamp, user_id, action, success/failure).

Мотивация:
Почему нужно добавить логирование?

-В настоящий момент поддержка разбирает проблемы по рассказам клиентов — это долго и неэффективно.
-Логирование позволит быстро выявлять ошибки и нестандартные ситуации в работе систем.
-Улучшит качество поддержки, ускорит отладку и повысит удовлетворённость клиентов и операторов.
-Позволит собирать статистику для улучшения процессов и обнаружения узких мест.
-Снизит время простоя и позволит быстрее реагировать на инциденты.

Технические и бизнес-метрики, которые улучшит логирование:

-Время обнаружения и устранения инцидента.
-Количество повторяющихся ошибок.
-Среднее время обработки заказов (по статусам).
-Количество жалоб клиентов на задержки и ошибки.
-Уровень SLA по времени ответа системы.

Предлагаемое решение:
- В качестве решения мы будем использовать ELK стек (Elasticsearch, Logstash, Kibana) для централизованного логирования.
- Elasticsearch будет использоваться для хранения и поиска логов.
- Logstash будет собирать логи из сервисов и отправлять их в Elasticsearch.
- Kibana будет использоваться для визуализации логов и создания дашбордов.
- Filebeat будет установлен на каждом сервисе для отправки логов в Logstash.
На схеме C4.drawio [./C4.drawio] показано, как будет выглядеть логирование в нашей системе.

Безопасность:
- Мы будем использовать VPN для доступа ко всей инфраструктуре логирования, чтобы обеспечить безопасность и защиту данных. На схеме это отображено.
- Доступ к инфраструктуре будет ограничен только для разработчиков и DevOps-инженеров.

Алертинг:
Основные причины настройки алертов:

-Реагирование в реальном времени. Алерты помогают быстро узнать о проблемах, а не обнаруживать их по отчетам или жалобам.
-Автоматизация контроля состояния системы. Позволяет не держать постоянно в фокусе все метрики, а получать уведомления при выходе показателей за установленные нормы.
-Снижение времени простоя и оперативное исправление.

Приблизительные метрики для алертов:
- Количество ошибок 5xx в API (если превышает 5% от общего числа запросов за 5 минут).
- Время ответа на запросы к API (если превышает 2 секунды в 95% случаев за 5 минут).
- Количество запросов к API (если превышает то это возможно DDOS).
